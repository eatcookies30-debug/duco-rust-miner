# Duino-Coin Rust Miner for Arduino AVR boards

A Duino-Coin AVR mining setup, in four pieces:

* **`miner/`** - a replacement for `AVR_Miner.py` written in Rust with **no
  external crates** (std only), so there is nothing to install with pip.
* **`firmware/board_sketch/`** - one sketch for every AVR board the rig supports.
  Its SHA-1 nonce search is an AVR assembly core generated by
  `firmware/board_sketch/gen_asm.py`, because GCC cannot keep SHA-1's five
  32-bit state variables in registers on the AVR. A board with 64 KB of flash
  gets the unrolled core, an ATmega328P board gets the looped one that fits in
  30 KB. Every board takes jobs over USB serial *and* over an I2C rig bus.
* **`firmware/i2c_rig/`** - the rig master: the board in the middle of the rig
  that feeds jobs to everything on the bus and hands the shares back to the
  miner over USB.
* **`firmware/baremetal/`** - the same protocol for chips that have no room for
  an Arduino sketch at all: ATmega8, ATmega16, ATmega168/328, and the ATtiny45
  and ATtiny85. Plain C driven straight from the registers, built with
  `avr-gcc` and flashed with `avrdude`.

Everything speaks the standard **DUCO-S1** protocol, so the pool, the difficulty
handling, the reward and the account are exactly the same as with the official
miner. Only the speed and the reliability change.

## Results

These are live figures from the bench this repo was built on: one Mega 2560
plugged into the PC, and six Nano 328P clones hanging off a second Mega 2560
that acts as the rig master, all mining at the same time. The per-board rates
are what `duco-miner --bench` measures (a difficulty-10 job with a nonce known
in advance, timed by the board itself); the rig total is what a real pool run
reports.

| firmware | board | flash | RAM | H/s |
|---|---|---|---|---|
| `firmware/board_sketch` | Mega 2560 | 37,208 B (14%) | 1,513 B | 1,782 |
| `firmware/board_sketch` | Nano 328P clone | 26,644 B (86%) | 1,513 B (73%) | 1,757 |
| `firmware/i2c_rig` (master) | Mega 2560 | 13,652 B (5%) | 2,463 B | - |
| `firmware/baremetal` | Nano 328P clone | 4,552 B (14%) | 713 B | 763 |
| `firmware/baremetal` | ATmega8 | 4,298 B (52%) | 729 B | not run |
| `firmware/baremetal` | ATtiny45 | 3,968 B (97%) | 114 B | not run |
| `firmware/baremetal` | ATtiny85 | 3,968 B (48%) | 114 B | not run |

The whole rig - one Mega on USB plus six Nanos on the bus - runs as **seven
miners at 12.37 kH/s**, and a 200 second run of that had 224 accepted shares and
nothing rejected, with every board reporting 1.76 kH/s for itself the whole time.

Against the stock 4.3 sketch on the same boards: 5.3x on a Mega, 5.2x on a
Nano. The Nano's 1,757 H/s over the I2C bus is 1% below what the same board
measures over USB serial, so sharing the bus costs almost nothing.

Kolka pays roughly `2 * ln(reported hashrate) / reward_div` per accepted share
with a `0.96^(miners - 1)` penalty, so hourly income goes like
`hashrate * ln(hashrate)`, not like hashrate alone.

## Requirements

* A board. `firmware/board_sketch` builds for a **Mega 1280/2560** or an
  **ATmega328P** board - Nano, Uno, Pro Mini. The unrolled core does not fit in
  a 328P: on its own it is 30,708 B, 99% of a Nano's 30,720 B of program flash,
  and with the Wire library added the build stops with
  `text section exceeds available space in board`. The sketch picks the core
  for you from the chip it is being compiled for, so there is nothing to choose.
* [`arduino-cli`](https://arduino.github.io/arduino-cli/installation/) to flash
  (the Arduino IDE works as well - open `firmware/board_sketch/board_sketch.ino`).
* Rust 1.70+ to build the miner. No crates, no network needed to build.
* `avr-gcc` and `avrdude` only for `firmware/baremetal`. `build.sh` finds the
  toolchain the Arduino IDE installed if there is no system one.
* Python 3 only for `gen_asm.py`, if you want to regenerate the assembly core.
* Linux is the platform everything here was tested on. The miner is plain std
  Rust, so it should work wherever a serial device can be opened by path (on
  macOS that is `/dev/tty.usbmodem*`). On Windows the `COM` ports are not
  openable that way - use the official Python miner there.

## Quick start

```bash
git clone https://github.com/eatcookies30-debug/duco-rust-miner
cd duco-rust-miner

# 1. flash the boards. flash.sh detects every port arduino-cli can see:
./scripts/flash.sh firmware/board_sketch
#    or name the ports:
./scripts/flash.sh firmware/board_sketch /dev/ttyACM0 /dev/ttyACM1
#    a Nano clone on a CH340 chip shows up as "Unknown", so it needs --board:
./scripts/flash.sh --board arduino:avr:nano firmware/board_sketch /dev/ttyUSB0

# 2. flash the rig master (the board in the middle of the bus)
./scripts/flash.sh firmware/i2c_rig /dev/ttyACM1

# 3. build the miner
cd miner && cargo build --release

# 4. see what the boards can actually do, offline, without an account
./target/release/duco-miner --bench --ports /dev/ttyACM0 --rig /dev/ttyACM1

# 5. mine
./target/release/duco-miner --user your_username \
    --ports /dev/ttyACM0 --rig /dev/ttyACM1 --key your_mining_key
```

You can point the miner at the official miner's config file instead of passing
ports and keys:

```bash
./target/release/duco-miner --config "Duino-Coin AVR Miner 4.3/Settings.cfg"
```

`Settings.cfg.example` is a template; copy it to `Settings.cfg` and fill it in.
Both `avrport` (boards plugged into the PC) and `rigport` (the rig master) are
read from it.

`./scripts/start-rig.sh` does step 5 for the whole rig in one command, and
`scripts/rig-shortcut.desktop` is a desktop shortcut for it. See
[One shortcut for the whole rig](#one-shortcut-for-the-whole-rig).

## Each board's number on the rig

There is nothing to pass on the command line when flashing. Every board's
address is a line at the top of its own sketch:

```c
#define SLAVE_ADDRESS 1     // this board's number on the I2C rig, 1 to 126
#define RIG_BUS_KHZ   100   // the bus speed in kHz
```

Open the sketch, change the number, flash, change it again for the next board.
That is the whole procedure.

* **`SLAVE_ADDRESS`** is the board's number on the bus. The pool counts a board
  by its number, so two boards with the same number behave as one miner. Set it
  to **0** for a board that is not wired to a bus at all - it then mines over
  serial only, which is what a Mega plugged straight into the PC does.
* **`RIG_BUS_KHZ`** is the bus speed. 100 is fine for short leads; use 50 when
  the wires are long or replies start getting dropped. ATtiny boards need 10 or
  less, see [Boards too small for a sketch](#boards-too-small-for-a-sketch).

The rig master has the same idea in its own USER SETTINGS block: `MAX_SLAVES`,
`RIG_BUS_KHZ`, `FIRST_ADDRESS` / `LAST_ADDRESS` (which board numbers to look
for), `RESCAN_SECONDS` (how often it walks the bus again, so a board plugged
in later joins without restarting anything), `STAT_SECONDS` (how often it reports
the health of the bus while the miner is driving it) and `MAX_SEARCH_MS` (how long
a board may search one job before the master gives up on that job and sends it
another).

The master keeps a job line and a reply line for every board it drives, so a
328P board acting as the master tops out at three boards: six boards need 2,463
bytes of RAM and an Uno or Nano has 2,048. Anything bigger is a Mega, which has
8,192 bytes and drives the six boards on this rig with 30% of its RAM used.

If `SLAVE_ADDRESS` is set to a number another board already holds, the sketch
retries a few times and then falls back to walking 1 to 126 and taking the first
free number, so the board keeps mining instead of sitting out. It always prints
the number it ended up with:

```
I2C slave address: 6
```

## Wiring a rig

Every slave hangs off the same two wires, so a rig of N boards on one master is
three nets, not N pairs:

```
                master  (Mega, Uno, ESP32, ...)
                SDA ─┬─ A4 ─ A4 ─ A4 ─ A4 ─ ...
                SCL ─┼─ A5 ─ A5 ─ A5 ─ A5 ─ ...
                GND ─┴─ GND ─ GND ─ GND ─ GND ─ ...
```

Use each board's TWI pins, which are not the same pins on every family:

```
ATmega328P (Nano, Uno, Pro Mini):  SDA = A4,  SCL = A5
ATmega1280/2560 (Mega):            SDA = D20, SCL = D21
```

The Mega is the trap: its I2C lines are digital pins 20 and 21, not its analog
A4/A5, so wiring a Mega to A4/A5 connects it to nothing. The sketches know which
pins belong to the bus and turn on the internal pull-ups on them; a 328P board
needs those because it has no external resistors on the lines, and a Mega 2560
has them onboard already.

Every board's pull-up ends up in parallel, so each board you add makes the lines
stronger: ten 328P boards give roughly 4 kOhm on each line, which the bus is
happy with. Bus capacitance grows with every board and every foot of wire, so
keep the leads short, and if replies start getting dropped, cut
`RIG_BUS_KHZ` to 50 before blaming a board.

## One shortcut for the whole rig

`scripts/start-rig.sh` starts everything with one command, and
`scripts/rig-shortcut.desktop` is a template for a desktop shortcut that does the
same thing from the GUI:

```bash
./scripts/start-rig.sh                              # reads ./Settings.cfg
./scripts/start-rig.sh "Duino-Coin AVR Miner 4.3/Settings.cfg"
./scripts/start-rig.sh --config ./Settings.cfg --rounds 10
```

It builds the miner if the binary is not there yet, then runs one process that
drives every board: the boards listed in `avrport`, and every board behind the
rig master in `rigport`. A board already mining does not take a second job, and
a lock file per set of ports (`/tmp/duco-miner-<ports>.lock`) stops two
instances from reading the same boards.

To put the shortcut on your desktop, copy `scripts/rig-shortcut.desktop` to
`~/.local/share/applications/`, change the `Exec=` line to your path, and
launch it from the desktop's application launcher.

## Command line

| flag | meaning |
|---|---|
| `--config FILE` | read username, ports, key and timeouts from the official `Settings.cfg` |
| `--user NAME` | Duino-Coin username |
| `--key KEY` / `--mining-key KEY` | mining key (base64 or plain; see below) |
| `--ports /dev/ttyACM0,/dev/ttyACM1` | serial ports of boards plugged into the PC |
| `--rig /dev/ttyACM1` | port of a rig master; the boards behind it are discovered automatically |
| `--pool ip:port` | skip the pool picker and use a specific node |
| `--tier AVR\|MEGA\|ARM\|DUE` | force the difficulty class instead of deriving it from the measured hashrate |
| `--report-time SECS` | how often to print the running totals (default 60) |
| `--board-timeout SECS` | deadline for one board to answer one job (default 120) |
| `--rounds N` | stop after N shares (useful for testing) |
| `--bench` | hashrate test straight against the boards, no network, no account |
| `--ping` | print the pool node the picker gives you and its greeting round trip |
| `--no-color` | turn off the ANSI colours |
| `--version` / `-V` | print the miner version (put it in bug reports) |
| `DUCO_DEBUG=1` | dump the raw bytes the boards send, with timestamps, to stderr |

`DUCO_MINING_KEY=<key>` is read from the environment too. `Settings.cfg` keys
that are honoured: `username`, `avrport`, `rigport`, `mining_key`,
`identifier` (the rig identifier sent with each share, one per board),
`periodic_report`, `avr_timeout` (how long a board has to answer one job) and
`soc_timeout` (how long the pool socket has to answer one request).

Colours are left out automatically when the output is not a terminal - a pipe,
a redirect, a shortcut that captures the output - or when `NO_COLOR` is set, so
the same lines stay readable when they are saved to a file.

## The mining key

Duino-Coin accounts can have a **mining key**: a secret sent with every job
request so nobody who only knows your username can mine into your balance. The
official `AVR_Miner.py` stores it **base64-encoded** in `Settings.cfg`:

```
mining_key = aGVsbG8=      # the key is "hello"
```

The miner here understands both the encoded and the plain form, and it checks
the key against the account service **before** mining so a wrong key is not
quietly ignored:

```
account your_username: mining key accepted
```

Use `scripts/set-mining-key.sh` to store a verified key:

```bash
./scripts/set-mining-key.sh                     # asks, verifies, saves
./scripts/set-mining-key.sh "your key"          # non-interactive
./scripts/set-mining-key.sh --clear             # remove it
```

It points at `./Settings.cfg` by default, or at the file named by
`DUCO_SETTINGS`. Base64 is obfuscation, not encryption: keep the file out of the
repo (it is gitignored) and do not paste it into an issue.

`scripts/balance.sh` prints the balance, the trust score, the number of miners
the account allows, the registered miners, and whether the key in Settings.cfg
is the one the account expects.

## Difficulty tiers

The pool accepts a share only when the difficulty it assigned is close to the
hashrate it measured - roughly hashrate/17 to hashrate/5. A board that asks for
a tier its speed does not support gets the share back as
`BAD Too high starting difficulty` or `BAD Too low starting difficulty`.

So the tiers the miner requests are the ones the pool will actually accept:

| measured hashrate | tier | difficulty the node assigns |
|---|---|---|
| 2,400 H/s and up | DUE | 512 |
| 600 - 2,400 H/s | ARM | 128 |
| 113 - 600 H/s | MEGA | 24 |
| under 113 H/s | AVR | 10 |

Each board is measured once at the start of a session with `--bench`'s test job,
and if the node still complains, the miner steps the tier one up or one down
and carries on. It does not do that if you named a tier yourself with `--tier`,
since that is an explicit request.

## The on-board LEDs

Every board's LED blinks while it is searching and double-flashes for each share
it finds. Blinking during a search needs a timer interrupt, because the search
itself is one long blocking call and nothing else runs while a board is working:

```c
ISR(TIMER1_COMPA_vect) {
  if (ledSearching) LED_PORT ^= LED_BIT;
}
```

Pin 13 is the LED on every board this is built for, but it is not the same port
bit everywhere: on the ATmega328P and ATmega168 pin 13 is bit 5 of port B, on
the ATmega1280/2560 it is bit 7. Writing the port directly is what makes it
possible from inside the interrupt - `digitalWrite()` cannot be called there.
One blink every 200 ms is a hundred instructions a second, which is nothing
next to a SHA-1.

The rig master's LED double-flashes for every share from any board on the bus,
so the master is the board you watch: it flashes six times a second on a full
six-board rig, and the slaves do not need to be visible to tell you the rig is
working.

## The rig master's serial protocol

The Rust miner talks USB serial only. A rig master is what turns that into a
bus. With `duco-miner --rig /dev/ttyACM1` the master takes its jobs from
the miner and answers with shares:

```
to the master:      MODE rig                    switch off the self-test
                    GIVE <addr> <prev>,<target>,<diff>
                    PING
from the master:    RIG <addr> <addr> ...       the boards on the bus
                    SHARE <addr> <nonce>,<elapsed>,<DUCOID>
                    BUSY <addr>                 that board is still searching
                    MISS <addr> <reason>        that board never answered
                    STAT <report>               bus health, only when it changed
```

Every `STAT` line is a thing to look at, because a clean bus says nothing. The
miner repeats it as a warning, and the report names the board that is losing
bytes:

```
[bus] /dev/ttyACM1: 6 boards, 410 jobs sent, 408 shares, 0 jobs never answered, 0 searches cut short, 3 of 37720 job bytes refused by a board, board 4 refused 3, 10542 H/s across 6 mining boards
```

Without `MODE rig` the master runs its own self-test: it walks addresses 1 to
126, hands each board a job whose answer it already knows (SHA-1 of
`ba29a15896fd2d792d5c4b60668bf2b9feebc51d` + `9999`), and prints what came
back. That is the quickest way to find out whether a board on the bus is alive:

```
Slave at address 1
slave 1: nonce 9999 OK, 1757 H/s  (18/18 so far)
Totals: 6 slaves, 160 jobs, 154 correct, 0 wrong, 0 of 13760 job bytes unacked, 10542 H/s across the 6 mining slaves
```

That run on this rig took 150 seconds: 160 jobs out, every board answering with
the nonce the master expected, no board dropping, and not one job byte refused
by a board.

Over the bus the reply is **decimal**; on the serial port it is **binary**. That
is what the reference rig implementations do, and it is why an ESP rig master
and the Rust miner read the same field differently.

Board identity deserves a note, because it is where rigs go wrong. A board's
name at the pool is the sixteen hex digits of the eight byte device id in its
boot signature row. Clone boards often ship with that row blank, in which case
every board of that kind reads 0xFF and reports the same id, and the pool counts
them as one miner. The address the board claims is written into the last two
digits of the id, which keeps it the length the protocol expects and makes each
board its own:

```
signature row 3A 7F 2C 91 4D 6E 0B 58, address 1  ->  DUCOID3A7F2C914D6E0B01
signature row 3A 7F 2C 91 4D 6E 0B 58, address 2  ->  DUCOID3A7F2C914D6E0B02
signature row all 0xFF,              address 3  ->  DUCOIDFFDFFFDFFFFFFF03
```

A board that never joins a bus has no address to fold in, so it keeps the plain
id its signature row gives it.

On the bus the master pushes `prevHash,targetHash,difficulty\n` one byte per
transmission, and the board answers `nonce,elapsedMicros,DUCOID\n` one byte at a
time in response to `requestFrom(address, 1)`. While the search is still running
every poll is answered with a bare `\n`, which is how the reference masters read
"nothing yet" and simply poll again. The search runs in the main loop while the
TWI interrupts serve the bus, so a board answering a rig is still mining.

Three things the glue has to get right, because each is easy to get wrong in a
way that makes a board look dead rather than slow:

* **the master keeps pushing while the board is still searching.** The job
  buffer is a 256 byte ring, about three jobs wide. `jobHead` is written only by
  the receive interrupt and `jobTail` only by the main loop, so consuming one job
  cannot lose the bytes of the next one. When the ring is full the interrupt
  ignores further bytes and sets a flag, and the main loop clears the whole buffer
  before reading it again: a half stored job is dropped rather than spliced onto
  the bytes that follow it, which would otherwise parse as a job with the wrong
  hashes.
* **the interrupt fills the buffer while the main loop is scanning it.** The scan
  for a job's newline has to compare against the length it snapshotted when it
  started. Comparing against the live length instead makes a job still in transit
  look finished at the point the scan has reached, one character is dropped, the
  hashes come out short, the job is refused, and the board never answers.
* **a byte can be lost on the bus.** A byte the board does not acknowledge is
  sent again; if it still does not get through, the board is left holding half a
  job line and nothing can take those bytes back. The master then sends a newline
  so the board throws the half line away, and sends the whole job again. If the
  job cannot be delivered at all the master says `MISS <address> job never
  reached the board`, so the miner tries a new job at once instead of waiting out
  the whole allowance. On the board's side, a job line that arrives whole but
  malformed is answered with a zero nonce rather than silence - the miner checks
  the hash, sees it is not the nonce it asked for, and sends the job again.

All of it is counted. Every `STAT_SECONDS` seconds (30 by default) the master
reports what the counting shows, and the miner prints it as a `[bus]` warning -
jobs sent, shares received, boards that went silent, and how many job bytes a
board refused to take. A clean bus prints nothing at all, so when a line appears,
lower `RIG_BUS_KHZ` to 50 and check the wiring.

That last part matters more than it looks. On a six board rig the first version of
this firmware lost about half the boards within a minute: one dropped byte made a
job unmineable, the board said nothing, the master kept believing it was still
searching and never sent it another job, and those boards sat idle for the rest of
the run. With the newline and the whole-line retry, a 224 share run had nothing
rejected and all six boards measured 1.76 kH/s for the whole session.

The AVR's serial receive buffer is 64 bytes and cannot be enlarged from a
sketch, so the master feeds a job line in 16 byte chunks and drains the serial
port during every wait. Wire has no TWI timeout either: a board that never
answers makes `requestFrom` sit until the bus is abandoned, which is why the
master checks that SDA and SCL are both high before it starts a transaction. A
START issued in the middle of somebody else's transaction leaves the TWI module
waiting for a start condition with SDA held low, and that jams the bus for every
board on it.

As a backstop, `MAX_SEARCH_MS` in the master's USER SETTINGS bounds how long a
board may search one job (90 s by default, roomy for the 65,501 hash maximum). If
a board says nothing for longer than that, the master clears the flag and sends it
the job the miner queued. Raise it if you hang slow boards off the bus - an ATtiny
on its factory 1 MHz clock needs far more than 90 s for a big job.

## Boards too small for a sketch

An ATmega8 has 8 KB of program flash, and the ATtiny45 and ATtiny85 have 4 KB
and 8 KB. The standard Arduino AVR core has no board definition for any of
them, and even a skeleton sketch that takes a job over Serial and answers on the
Wire bus measures 5,514 B on a 328P before the board id, the timing and the
reply line are added. `firmware/baremetal` is the firmware for those boards:
the same protocol and the same reply line, driven from registers, with no
Arduino libraries at all.

```bash
cd firmware/baremetal
./build.sh                 # atmega328p, atmega168p, atmega8, attiny45, attiny85
./build.sh atmega8
F_CPU=1000000 ./build.sh attiny45     # a chip still on its factory 1 MHz
```

and then:

```bash
avrdude -c arduino -p atmega328p -P /dev/ttyUSB0 -U flash:w:duco_atmega328p.hex
avrdude -c usbtiny   -p attiny45  -P /dev/ttyUSB0 -U flash:w:duco_attiny45.hex
```

The board then speaks the same protocol as the sketches, so the Rust miner and
the rig master drive it without any change.

**The core** (`tiny_hash.c` for the ATmega, `attiny_hash.c` for the ATtiny) is a
single looped round body:

* the schedule is a **16-word rolling window** rather than 80 words. `W[i]` is
  read back at rounds `i+3`, `i+8`, `i+14` and `i+16`, and the round that
  overwrites slot `i & 15` is round `i+16` - the last round that word is needed
  in - so 64 bytes of RAM is enough instead of 320;
* rounds 0-9 depend only on the previous hash, not on the nonce, so they are
  computed **once per job** and the search starts from that state;
* the nonce is walked as **decimal digits** instead of being formatted every
  attempt, so the search loop never divides;
* the state is plain local variables, so GCC decides where it lives. On a 328P
  it stays in registers; on an ATtiny45, which has 24 registers in total, some of
  it spills to the stack and the hash still runs.

The digests both cores produce were compared against Python's `hashlib` over
20,000 previous-hash and nonce pairs.

**ATmega8, ATmega16, ATmega168, ATmega328P** all have a TWI module and a UART,
so `duco_tiny.c` drives both from the registers: a TWI slave interrupt handler,
a UART driver, the DUCOID read out of the boot signature row, and Timer 1 to
time a search.

| chip | flash | RAM |
|---|---|---|
| ATmega328P (Nano, Uno) | 4,552 B | 713 B |
| ATmega168P | 4,552 B | 713 B |
| ATmega8 | 4,298 B | 729 B |
| ATmega16 | 4,434 B | 729 B |

**ATtiny45 and ATtiny85** have neither a TWI module nor a UART, so they cannot
run a sketch and cannot be handed a job over serial: the only way to give one a
job is to hang it off a rig master on the bus. `duco_attiny.c` bit-bangs the bus
from the pin-change interrupt - SDA and SCL on PB0-PB5, which is the only port
these chips have pin-change interrupts on - driven open-drain, one bit per
interrupt. At 8 MHz that comfortably keeps up with a 10 kHz bus, so the rig
master's `RIG_BUS_KHZ` has to be 10 or less for ATtiny boards.

| chip | flash | RAM | |
|---|---|---|---|
| ATtiny45 | 3,968 B of 4,096 B | 114 B of 256 B | 128 B of flash and about 70 B of RAM left over |
| ATtiny85 | 3,968 B of 8,192 B | 114 B of 512 B | |
| ATtiny25 | 3,940 B of 2,048 B | 114 B of 128 B | does not fit, see below |

**Why the ATtiny25 cannot do it.** It is the smallest of the family: 2 KB of
flash and 128 bytes of RAM. SHA-1's working set alone is 104 bytes - a 16-word
schedule window (64), the previous hash (20), the target digest (20) - and the
round loop needs a stack frame on top of that: seven live 32-bit values is 28
registers, and the AVR has 24 usable ones, so the extras spill to the stack.
`attiny_mine` alone pushes 18 registers, and the bus interrupt pushes 15 more on
top of it. Measured with the driver, the leanest honest version of this miner is
3,940 bytes of flash and 114 bytes of globals plus roughly 70 bytes of stack.
The ATtiny25 is out on both counts - nearly twice the flash and more RAM than the
chip has - so **the ATtiny45 is the smallest ATtiny a DUCO-S1a miner can run
on**. `build.sh` still accepts `attiny25` if you want to see the numbers for
yourself.

Wiring an ATtiny board to the rig: SDA and SCL to the same two lines the master
uses, GND to GND, with the master's pull-ups still on the bus. The chip needs an
ISP programmer (`usbtiny`, an AVRISP mkII, or an old Arduino in the ISP bridge);
there is no bootloader on these chips, so arduino-cli cannot upload to them.

None of the ATtiny firmware has been run on ATtiny hardware here - the hash
core and the parser are checked on a desktop, the sizes are measured with
avr-gcc 7.3.0, and the bus state machine is the same one the ATmega driver uses,
bit by bit. Treat it as a starting point, not a bench-tested rig.

## Why the assembly core is faster

GCC ends up spilling SHA-1's state to RAM: 70 unrolled rounds need 24 live
registers, and the AVR has 32, of which the compiler needs some for addressing
and the digit counter. The generated core instead keeps the state in six
register groups that **rotate** through the `a,b,c,d,e` roles one group per
round, so the role shift is a change of which group the next round names -
**no copies at all**:

```
G0 r16-19   G1 r20-23   G2 r2-5   G3 r6-9   G4 r10-13
G5 r14,r15,r30,r31      scratch: r24-27
```

What that buys over the C version:

* **no state copies** - the round's new `a` is accumulated directly in the group
  the previous round's `e` vacated (the C version spends 8 `movw` pairs a round
  on this);
* **phase constants in four instructions** - AVR has no `add reg, imm`, and only
  r16-r31 take immediates at all. Pinning the scratch group to r24-r27 lets
  `+0x5a827999` be done with `subi/sbci` of the two's complement (4 cycles)
  instead of four `lds` plus four `add` (12 cycles): 3.5% of the whole hash;
* **schedule words 16, 17 and 20 are written by C once per job** - they never
  depend on the nonce, so the core does not reload them into scratch every
  attempt (24 memory instructions per hash);
* **the digest compare is lazy** - only the most significant byte of the first
  word is loaded for the ~99.9% of attempts that fail there;
* **the last three schedule rounds skip their store** - a word is only read back
  three, eight, fourteen and sixteen rounds later, so rounds 77-79 never need to
  write it out.

The unrolled core is 7,453 instructions / 8,737 cycles at 16 MHz, i.e. 549 us
per hash, which is within 1% of the instruction-count floor. The schedule (16
`lds` + 12 `eor` + 5 shifts + 4 `sts` per round, 61 rounds) is 40% of the work,
`lds`/`sts` cost two cycles whatever the addressing mode, and the AVR has no
barrel shifter, so `rotl5` is unavoidably a 20-instruction `rol` chain.

The unrolled core does not fit on a 328P, so the sketch for those boards uses a
core written to be small. Both come from the same generator:

```bash
cd firmware/board_sketch
python3 gen_asm.py duco_rounds_mega.h            # the unrolled core
python3 gen_asm.py --compact duco_rounds_328p.h # the looped core
```

The role shift repeats every six rounds, so the compact core cuts each 20-round
phase into a six-round body that runs three times, with the leftover rounds
emitted inline: 3,625 instructions of code instead of 7,453, which is the 8 KB a
Nano does not have. Inside the loop body the schedule pointer `Z` stands in for
the absolute `MSG[...]` addresses - a round stores at `Z+60` and steps back to
the next round's base - and since `Z` advances exactly four bytes a round,
comparing its low byte against the end of the window is the loop test, so there
is no counter register at all. The instruction and cycle counts the generator
prints are the emitted code, not the code executed: the compact body is jumped
through three times per phase, so a Nano hash still runs 70 rounds.

Giving up that code size costs a little speed: on the same Nano the unrolled core
measures 1,815 H/s and the looped core 1,757 H/s, about 3% apart. The compact
group set is also one register pair different - it uses r28:r29 for part of the
state instead of r30:r31, because r30:r31 are needed for the pointer - and since
r28:r29 is the pair GCC uses as the stack frame pointer, the compact core pushes
and pops them on entry and before every return, which is what makes it safe to
call from a function with local variables.

`duco_hash.cpp` is the one file that decides which core a board gets: it
includes `duco_rounds_mega.h` on a chip with room for it and
`duco_rounds_328p.h` on one that does not.

## AVR gotchas worth knowing

Each of these is a plausible way to end up with a board that hashes silently
wrong. The first list is what the generator has to get right:

* `lds`/`sts` move **one byte**, not a 32-bit word - a 32-bit value needs four of
  each. The classic "LDS loads two bytes" mistake leaves every odd register
  holding garbage;
* `ldi`, `subi`, `sbci` only work on r16-r31, which is why the scratch group is
  pinned to r24-r27;
* `r1` is the zero register by ABI - the rotate-by-1 uses `adc reg, r1`;
* `r0` is ordinary writable space. It is easy to assume the first register is
  reserved, so a probe on a Nano (`mov r0, r4`, then shifting r4 left through r0)
  was run before the rotate-by-5 and rotate-by-30 helpers were written to use it
  as scratch;
* `ldd`/`std` displacements are a 6-bit field, so a pointer reaches 63 bytes at
  most. That is why the compact core's schedule window is 60 bytes wide and
  steps with `adiw r30, 60` then `sbiw r30, 56`; the immediate in `adiw`/`sbiw`
  also tops out at 63, and there is no `subiw` at all;
* conditional branches reach only 63 words, so the compare's failure handlers are
  inlined per word instead of chained to one distant label;
* the hit flag must come back as an inline-asm output register, not a global:
  without a memory clobber GCC hoists the global's load out of the nonce loop and
  every attempt looks like a miss;
* globals referenced only from asm must be non-`static` and marked
  `__attribute__((used))`, because arduino-cli builds with `-flto` and otherwise
  deletes them;
* `.inc` files are not reliably copied by arduino-cli, so the generated core is
  included as a `.h`;
* **Timer 1's compare-match interrupt is `TIMER1_COMPA_vect`, not the overflow
  vector.** A timer set to clear itself on compare match never reaches the
  overflow, so an `ISR(TIMER1_OVF_vect)` blinks nothing and looks like a broken
  LED rather than a wrong vector;
* **pin 13 is not the same port bit on both families** - bit 5 of port B on a
  328P, bit 7 on a 1280/2560. Writing the port directly with the wrong bit drives
  an unused pin and the LED never moves.

Four more that only bite a build with no Arduino libraries in it, like
`firmware/baremetal`:

* **AVR's `int` is 16 bits wide**, so a literal shifted past that width loses
  bits. `tail[...] |= 0x80u << 24` is a shift past the width of the type the
  literal is written in, and the SHA-1 padding byte quietly disappears from the
  message. On a board it looks like a core that finds two- and three-digit nonces
  and misses one- and four-digit ones. A desktop cannot catch this, because there
  the same expression is well defined.
* **TWCR is not a set/clear register.** Every write replaces the whole byte, so an
  acknowledge that leaves `TWIE` out switches the bus interrupt off for good. The
  board then answers the first poll and never answers again, and the master hangs
  waiting for a transmission that will never finish.
* **A START that never completes has to be abandoned by turning the module off**
  (`TWCR = 0`). With `TWEN` still set and `TWSTA` pending, the TWI keeps asking
  for a start condition and holds SDA low, which jams the bus for everything
  attached to it, the board that did it included.
* **The baud divisor has to be rounded.** `(F_CPU/16 + BAUD/2)/BAUD - 1` is UBRR 8,
  i.e. 111,111 baud, 3.5% off the 115,200 a PC asks for; truncating
  `(F_CPU/16)/BAUD - 1` gives UBRR 7, 125,000 baud, 8.5% error, and the replies
  arrive as garbage. 3.5% is well inside what both ends tolerate, which is why the
  miner at 115200 reads a bare-metal board fine.
* **The ATtiny25/45/85 have no TWI and no UART at all**, and only one pin-change
  interrupt vector, `PCINT0_vect`, covering PB0-PB5. Their timers are 8-bit:
  Timer 1's compare match is `TCCR1`'s `CTC1` bit with `CS13` for the /1024
  prescaler, and `OCR1A` tops out at 255, so a 200 ms blink has to count matches
  rather than set a 1,600,000-cycle compare value. The signature row is read with
  `RSIG` in `SPMCSR`; avr-libc's `boot_signature_byte_get` wants `SIGRD`, which
  the ATtiny headers do not define, so the read is a few lines of hand-written
  asm.

## Troubleshooting

* **"text section exceeds available space in board"** - the unrolled core does
  not fit in an ATmega328P's 30,720 B of program flash: on its own, before the
  Wire library and the I2C glue, it is already 30,708 B. `board_sketch.ino`
  picks the looped core automatically for those chips, so this only happens if
  the chip macro does not match the board you are building for.
* **"Permission denied" opening `/dev/ttyACM0`** - serial ports belong to the
  `dialout` group on most Linux distros:

  ```bash
  sudo usermod -aG dialout "$USER"   # then log out and back in
  ```

* **A board that shows up as "Unknown" in `arduino-cli board list`** - it is a
  CH340 clone. arduino-cli cannot read its name, so pass the board explicitly:
  `--board arduino:avr:nano`.
* **"no reply from /dev/ttyACMx within Ns"** - the board was given a job and did
  not answer. The miner responds by reopening the port, which resets the sketch.
  If it happens to every board at once, the pool node is usually the cause, not
  the hardware: the node closes a connection whose share has not arrived, and a
  board left searching a dead job looks dead for the whole allowance.
* **Opening a port resets the board.** Opening a serial port toggles DTR, which
  restarts the sketch. After flashing, give a board a few seconds before the
  miner talks to it - the rig master needs time to walk the bus before it can
  answer `PING`.
* **Nothing answers on the I2C bus** - the two ends have to be on each board's
  TWI pins, which are not the same pins on every family (A4/A5 on a 328P,
  D20/D21 on a Mega), and both boards need a common ground. The rig master prints
  the pins it is using when it finds no slave. A slave that is still searching
  answers every poll with a newline, so a master that reads a line gets an empty
  one and polls again - that is the reference behaviour, not a hang.
* **A bare-metal board from `firmware/baremetal` prints nothing at boot** - it
  runs its UART at 111,111 baud (UBRR 8), which a 115,200 terminal reads
  correctly; a truncated divisor (UBRR 7, 125,000 baud) is 8.5% off and the
  replies come back as garbage. Before it prints anything the board walks
  addresses 1 to 126 looking for a free one, so if something else on the bus is
  holding SDA low at that moment it says `I2C: no free bus address`, mines over
  serial only, and retries the bus every five seconds. Flashing with avrdude
  writes only the application pages, so the bootloader is left alone and an
  Arduino sketch can be uploaded afterwards with arduino-cli.
* **"BAD Too high starting difficulty"** / **"BAD Too low starting difficulty"** -
  the node assigns difficulty from the hashrate it measured, and a board whose
  tier does not match its speed gets the share back. The miner steps the tier one
  up or one down and carries on, so this shows up once per board per connection,
  not repeatedly.
* **"BAD Incorrect result"** - a pool-side race: the node sends `prevHash` +
  `expectedHash`, the board spends seconds finding the nonce, and by the time the
  share is submitted the node has advanced the chain from other miners on that
  node, so the hash it recomputes uses a newer `prevHash`. Nothing in the
  firmware or the miner can avoid it, and it is why only accepted shares count.
* **Boards "time out" only when you run `--bench` while the miner is mining** -
  two processes reading the same serial port interleave each other's replies. The
  lock file stops the miner from doing this to itself; do not start a second one.
* **`--bench` takes minutes** - that is expected. A difficulty-655 job searches
  up to 65,501 hashes, about 36 s per run.

## How the PC-side miner differs from `AVR_Miner.py`

| | official `AVR_Miner.py` | this miner |
|---|---|---|
| dependency | Python + pip + `serial` + `requests` | one static binary, std only |
| serial port | reopened for every job, which resets the board | opened once per session; the board keeps running |
| serial read | no timeout | hard deadline per job, so a stuck board cannot stall the run |
| reply framing | takes whatever arrives | discards a reply left over from an abandoned job, then verifies `sha1(prevHash + nonce) == expectedHash` locally before submitting |
| board recovery | gives up after a few failures | reopens the port, which toggles DTR and resets the sketch |
| pool connection | reconnects on error | reconnects on EOF or timeout, and after three consecutive failures asks the pool picker for a different node |
| pool replies | one `recv(limit)` | line-based with the unread tail kept, so split or bunched replies are not lost |
| mining key | decoded, never validated | decoded **and** validated against the account service before mining |
| difficulty tier | fixed thresholds | derived from the measured hashrate, and corrected when the node rejects the tier |
| concurrency | nothing stops two instances | a lock file per port set (`/tmp/duco-miner-<ports>.lock`) |
| offline testing | none | `--bench`, against boards on serial or behind a rig master |

The Rust miner has unit tests for the SHA-1 implementation, the reply parsing,
the tier stepping and the rig bridge:

```bash
cd miner && cargo test
```

## Limitations

* The assembly cores have been run on Mega 2560 and Nano 328P boards. The
  generator emits instructions any AVR should execute, but only those two boards
  are exercised here.
* The I2C slave is the community rig protocol from
  `ricaun/DuinoCoinI2C`, and it was measured on a physical bus: six Nano 328P
  slaves on one Mega 2560 master at 100 kHz. The self-test passes with 366 jobs
  out, every reply the master collected correct and none of the 31,476 job bytes
  unacknowledged, and every board measuring 1,757 H/s for itself. Bytes do get
  lost on a real bus occasionally, which is why the master resends a whole job
  line when a byte fails three times and why the board answers a job line it
  cannot parse with a zero nonce instead of saying nothing. What has not been
  tested is a master from the reference rig implementations - ESP32, ESP8266,
  Raspberry Pi - since the master in this repo is its own.
* The bare-metal ATmega build was measured on an ATmega328P Nano and nothing
  else. The ATmega8 and ATmega168 builds compile against the same register-level
  TWI and UART driver, but no board of those kinds was run here.
* The ATtiny firmware has no hardware behind it. The hash core and the job
  parser were checked on a desktop and the sizes were measured with avr-gcc; the
  bit-banged bus has never seen a real ATtiny.
* The reward figures are measurements on one account over one period. Kolka's
  `reward_div` changes as the network's total hashrate changes, so the DUCO/hour
  numbers will drift; the *relative* speedups are the stable part.
* An account's miner allowance limits how many boards help. Check with
  `scripts/balance.sh` before wiring up a big rig.
* The pool-side share race ("BAD Incorrect result") is not fixable from the
  miner side.
* `Settings.cfg` stores the mining key base64-encoded. That is not safe to
  share; it is gitignored for that reason.

## Is a custom miner allowed?

The code is MIT licensed and the official Duino-Coin README lists community
miners, so publishing a fork is fine. Their terms of service are less clear-cut
about running one: they "recommend using only the official or verified mining
programs", and state that "attempting to create your own mining software, or
modifying an official program may lead to account suspension or banning ... if a
modified program were to have an issue". Community software is explicitly allowed
as long as it complies with the rules.

What actually gets accounts flagged, and what this project does not do:

* **reporting a hashrate the hardware cannot produce.** The number submitted is
  the board's own nonce count divided by the elapsed microseconds it printed,
  exactly the calculation `AVR_Miner.py` does, and the miner checks
  `sha1(prevHash + nonce) == expectedHash` locally before submitting.
* **using a difficulty tier the hardware is not suited for** - the terms forbid
  emulating a differently powered device. The tier here is derived from the
  measured hashrate, and since the 2025 pool migration the node assigns
  difficulty dynamically from the hashrate it measures, so the tier string is only
  a hint.
* **spamming the pool or exceeding the miner allowance.** One socket per board,
  reused until the node closes it, reconnect instead of a new connection, no
  second instance (lock file per port set), and a mining key so nobody else can
  mine under the username.

A question about this has been raised in the Duino-Coin Discord; this section
will be updated when a definitive answer arrives.
