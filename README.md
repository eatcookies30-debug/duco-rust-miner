# Duino-Coin Rust Miner for Mega 2560

A Duino-Coin AVR mining setup for the Arduino Mega 2560, made of two parts:

* **`firmware/asm_sketch`** - the sketch flashed onto the board. Its SHA-1 nonce
  search is a hand-written AVR assembly core generated by `firmware/asm_core`,
  because GCC cannot keep SHA-1's five 32-bit state variables in registers on
  the AVR.
* **`miner/`** - a replacement for `AVR_Miner.py` written in Rust with **no
  external crates** (std only), so there is nothing to install with pip.

Both parts talk the standard **DUCO-S1** protocol, so the pool, the difficulty
handling, the reward and the account are exactly the same as with the official
miner. Only the speed and the reliability change.

## Results

Everything below was measured on the same two Mega 2560 boards, with the same
benchmark (`miner --bench`, which asks each board for nonces 50, 9,999, 42,424
and 65,500 and reports the nonce and elapsed time the board itself prints).

| firmware | flash size | H/s per Mega 2560 | vs official | reward per board |
|---|---|---|---|---|
| `firmware/official_sketch` (stock 4.3) | 13,670 B | 338 | 1.00x | ~0.011 DUCO/h |
| `firmware/c_core` (optimised C) | 36,196 B | 1,239 | 3.66x | ~0.048 DUCO/h |
| `firmware/asm_sketch` (assembly core) | 37,928 B | **1,821** | **5.39x** | **~0.068 DUCO/h** |

Typical bench output for the assembly core:

```
/dev/ttyACM0: DUCOID1234567890ABCDEF - test nonce 50 in 28240 us -> 1770.54 H/s
  diff 100: found nonce 9999 in 5.496152 s -> 1819.27 H/s OK
  diff 655: found nonce 42424 in 23.288248 s -> 1821.69 H/s OK
  diff 655: found nonce 65500 in 35.9504 s -> 1821.95 H/s OK
```

Two boards at 1,821 H/s produce about 1,890 accepted shares per hour, and the
account balance grew by 0.135 DUCO/hour measured against `server.duinocoin.com`
(442 accepted shares in 14 minutes) - **+42% over the optimised C firmware and
6.4x over the stock 4.3 firmware**.

Kolka pays roughly `2 * ln(reported hashrate) / reward_div` per accepted share
with a `0.96^(miners - 1)` penalty, and difficulty is fixed at 128 for this
tier, so a miner also earns more shares per hour in proportion to its hashrate.
Hourly income therefore goes like `hashrate * ln(hashrate)`, not like hashrate
alone.

## Why the assembly core is faster

GCC ends up spilling SHA-1's state to RAM: 70 unrolled rounds need 24 live
registers, and the AVR has 32, of which the compiler uses for addressing and
the decimal-digit counter. The generated core instead keeps the state in six
register groups that **rotate** through the `a,b,c,d,e` roles one group per
round, so the role shift is a change of which group the next round names -
**no copies at all**:

```
G0 r16-19   G1 r20-23   G2 r2-5   G3 r6-9   G4 r10-13
G5 r14,r15,r30,r31      scratch: r24-27
```

What that buys over the C version:

* **no state copies** - the round's new `a` is accumulated directly in the group
  the previous round's `e` vacated (the C version spends 8 `movw` pairs a round
  on this);
* **phase constants in four instructions** - AVR has no `add reg, imm`, and only
  r16-r31 take immediates at all. Pinning the scratch group to r24-r27 lets
  `+0x5a827999` be done with `subi/sbci` of the two's complement (4 cycles)
  instead of four `lds` plus four `add` (12 cycles): 3.5% of the whole hash;
* **schedule words 16, 17 and 20 are written by C once per job** - they never
  depend on the nonce, so the core does not reload them into scratch every
  attempt (24 memory instructions per hash);
* **the digest compare is lazy** - only the most significant byte of the first
  word is loaded for the ~99.9% of attempts that fail there;
* **the last three schedule rounds skip their store** - a word is only read back
  three, eight, fourteen and sixteen rounds later, so rounds 77-79 never need to
  write it out.

The core is 7,453 instructions / 8,737 cycles at 16 MHz, i.e. 549 us per hash,
which is within 1% of the instruction-count floor. The schedule (16 `lds` + 12
`eor` + 5 shifts + 4 `sts` per round, 61 rounds) is 40% of the work and
`lds`/`sts` cost two cycles whatever the addressing mode, and AVR has no barrel
shifter, so `rotl5` is unavoidably a 20-instruction `rol` chain.

## Requirements

* An Arduino **Mega 2560**. The optimised cores are fully unrolled, so they need
  a board with room in program flash - they take 37,928 B on a Mega 2560 (14% of
  its 253,952 B). They **do not fit on an Uno, Nano or Pro Mini** (32,256 B total;
  the assembly core needs 37,324 B and the C core 35,592 B, measured with
  arduino-cli 1.4.1). On a 328P board use `firmware/official_sketch` (13,072 B),
  which is the stock 4.3 code and runs at about 340 H/s there.
* [`arduino-cli`](https://arduino.github.io/arduino-cli/installation/) to flash
  (the Arduino IDE works as well - open `firmware/asm_sketch/asm_sketch.ino`).
* Rust 1.70+ to build the miner. No crates, no network access needed to build.
* Python 3 only for the generator and the verification scripts, and for the two
  helper scripts. No third-party packages.
* Linux is the platform everything here was tested on. The miner itself is plain
  std Rust, so it should work wherever a serial device can be opened by path
  (on macOS that is `/dev/tty.usbmodem*`, on Windows the `COM` ports are not
  openable that way - use the official Python miner on Windows).

## Quick start

```bash
git clone https://github.com/eatcookies30-debug/duco-rust-miner
cd duco-rust-miner

# 1. flash the assembly core (detects the boards automatically)
./scripts/flash.sh firmware/asm_sketch
#    or explicitly:
./scripts/flash.sh firmware/asm_sketch /dev/ttyACM0 /dev/ttyACM1

# 2. build the miner
cd miner && cargo build --release

# 3. see what the boards can actually do, offline, without an account
./target/release/duco-miner --bench --ports /dev/ttyACM0,/dev/ttyACM1

# 4. mine
./target/release/duco-miner --user your_username \
    --ports /dev/ttyACM0,/dev/ttyACM1 --key your_mining_key
```

You can point the miner at the official miner's config file instead of passing
flags:

```bash
./target/release/duco-miner --config "Duino-Coin AVR Miner 4.3/Settings.cfg"
```

`Settings.cfg.example` is a template; copy it to `Settings.cfg` and edit it.

## Command line

| flag | meaning |
|---|---|
| `--config FILE` | read username, ports, key and timeouts from the official `Settings.cfg` |
| `--user NAME` | Duino-Coin username |
| `--key KEY` / `--mining-key KEY` | mining key (base64 or plain; see below) |
| `--ports /dev/ttyACM0,/dev/ttyACM1` | serial ports of the boards (up to 2) |
| `--pool ip:port` | skip the pool picker and use a specific node |
| `--tier AVR\|MEGA\|ARM\|DUE` | force the difficulty class instead of deriving it from the measured hashrate |
| `--report-time SECS` | how often to print the running totals (default 60) |
| `--board-timeout SECS` | deadline for one board to answer one job (default 120) |
| `--rounds N` | stop after N shares (useful for testing) |
| `--bench` | hashrate benchmark straight against the boards, no network, no account |
| `--mock` | run a fake pool node on 127.0.0.1:7913 and mine against it - tests the whole protocol without an account |
| `--ping` | print the pool node the picker gives you and its greeting round trip |
| `--version` / `-V` | print the miner version (put it in bug reports) |
| `DUCO_DEBUG=1` | dump the raw bytes the boards send, with timestamps, to stderr |

`DUCO_MINING_KEY=<key>` is read from the environment too. `Settings.cfg` keys
that are honoured: `username`, `avrport`, `mining_key`, `identifier` (the rig
identifier sent with each share, one per board), `periodic_report`,
`avr_timeout` (how long a board has to answer one job) and `soc_timeout` (how
long the pool socket has to answer one request).

## The mining key

Duino-Coin accounts can have a **mining key**: a secret sent with every job
request so nobody who only knows your username can mine into your balance. The
official `AVR_Miner.py` stores it **base64-encoded** in `Settings.cfg`:

```
mining_key = aGVsbG8=      # the key is "hello"
```

The miner here understands both the encoded and the plain form, and it checks
the key against the account service **before** mining so a wrong key is not
quietly ignored:

```
account your_username: mining key accepted
```

Use `scripts/set-mining-key.sh` to store a verified key:

```bash
./scripts/set-mining-key.sh                     # asks, verifies, saves
./scripts/set-mining-key.sh "your key"          # non-interactive
./scripts/set-mining-key.sh --clear             # remove it
```

It points at `./Settings.cfg` by default, or at the file named by
`DUCO_SETTINGS`. Base64 is obfuscation, not encryption: keep the file out of the
repo (it is gitignored) and do not paste it into an issue.

`scripts/balance.sh` prints the balance, the trust score, the number of miners
the account allows, the registered miners, and whether the key in Settings.cfg is
the one the account expects.

## How the PC-side miner differs from `AVR_Miner.py`

| | official `AVR_Miner.py` | this miner |
|---|---|---|
| dependency | Python + pip + `serial` + `requests` | one static binary, std only |
| serial port | reopened for every job, which resets the board | opened once per session; the board keeps running |
| serial read | no timeout | hard deadline per job, so a stuck board cannot stall the run |
| reply framing | takes whatever arrives | discards a reply left over from an abandoned job, then verifies `sha1(prevHash + nonce) == expectedHash` locally before submitting |
| board recovery | gives up after a few failures | reopens the port, which toggles DTR and resets the sketch |
| pool connection | reconnects on error | reconnects on EOF or timeout, and after three consecutive failures asks the pool picker for a different node |
| pool replies | one `recv(limit)` | line-based with the unread tail kept, so split or bunched replies are not lost |
| mining key | decoded, never validated | decoded **and** validated against the account service before mining |
| concurrency | nothing stops two instances | a lock file per port set (`/tmp/duco-miner-<ports>.lock`) |
| offline testing | none | `--bench` (boards only) and `--mock` (protocol only, no account) |

## Verifying the assembly core

The core is machine-generated, so it comes with the checks that generated it:

```bash
cd firmware/asm_core
python3 gen_asm.py                                    # instruction and cycle counts
python3 sim_check.py                                  # simulated AVR vs hashlib
```

which currently prints:

```
instructions: 7453  cycles: 8737
checked 205 nonces, failures: 0
random hash/nonce failures: 0
```

Three further levels of verification, in order of how much hardware they need:

1. **`sim_check.py`** - a small AVR simulator (only the opcodes the core uses)
   runs the generated core for 205 nonces plus 400 random hash/nonce pairs and
   compares the digest with Python's `hashlib`: 0 failures. This is what catches
   register-aliasing and flag bugs before they reach a board.
2. **`build_trace.py` + `trace_test/`** - builds a sketch that stores the state
   after every round and compares it with a C reference: `bad rounds: 0`.
3. **`hit_test/`** - a standalone sketch with hardcoded targets: finds nonce 50
   for the known digest and correctly reports "no match" for a wrong target.

`firmware/asm_core/board_probe.py` is a plain serial probe (no pool, no account)
for timing searches on a board; it needs `pyserial`:

```bash
pip install pyserial
python3 firmware/asm_core/board_probe.py /dev/ttyACM0
```

In addition, the miner re-computes `sha1(prevHash + nonce)` itself before
submitting any share, so a board that ever returned a wrong nonce would be
rejected by the miner rather than paid for.

The unit tests in the Rust miner cover the SHA-1 implementation, the binary
reply parsing, and the base64 mining-key normalisation:

```bash
cd miner && cargo test
```

## AVR gotchas the generator has to get right

Worth knowing if you want to change the core, because each of these is a
plausible way to get a board that hashes silently wrong:

* `lds`/`sts` move **one byte**, not a 32-bit word - a 32-bit value needs four of
  each. The classic "LDS loads two bytes" mistake leaves every odd register
  holding garbage;
* `ldi`, `subi`, `sbci` only work on r16-r31, which is why the scratch group is
  pinned to r24-r27;
* conditional branches reach only 63 words, so the compare's failure handlers are
  inlined per word instead of chained to one distant label;
* `r1` is the zero register by ABI - the rotate-by-1 uses `adc reg, r1`;
* the hit flag must come back as an inline-asm output register, not a global:
  without a memory clobber GCC hoists the global's load out of the nonce loop and
  every attempt looks like a miss;
* globals referenced only from asm must be non-`static` and marked
  `__attribute__((used))`, because arduino-cli builds with `-flto` and otherwise
  deletes them;
* `.inc` files are not reliably copied by arduino-cli, so the generated core is
  included as a `.h`.

## Troubleshooting

* **"Sketch uses 37324 bytes (115%) of program storage space"** - the optimised
  cores are fully unrolled and do not fit on an ATmega328P board (Uno, Nano, Pro
  Mini). Flash `firmware/official_sketch` on those boards instead; the assembly
  and C cores are for boards with at least 64 KB of program flash.
* **"Permission denied" opening `/dev/ttyACM0`** - serial ports belong to the
  `dialout` group on most Linux distros:

  ```bash
  sudo usermod -aG dialout "$USER"   # then log out and back in
  ```

* **"no reply from /dev/ttyACMx within Ns"** - the board was given a job and did
  not answer. The miner responds by reopening the port, which resets the sketch.
  If it happens to every board at once, the pool node is usually the cause, not
  the hardware: the node closes a connection whose share has not arrived, and a
  board left searching a dead job looks dead for the whole allowance.
* **"BAD Too high starting difficulty"** - normal, once per connection per board.
  The node starts the tier probe at difficulty 512 and then drops to 128; the
  first nonce found against the old target is not valid for the new one. The
  official miner loses the same shares.
* **"BAD Incorrect result"** - a pool-side race: the node sends `prevHash` +
  `expectedHash`, the board spends seconds finding the nonce, and by the time the
  share is submitted the node has advanced the chain from other miners on that
  node, so the hash it recomputes uses a newer `prevHash`. Nothing in the
  firmware or the miner can avoid it, and it is why only accepted shares count.
* **Boards "time out" only when you run `--bench` while the miner is mining** -
  two processes reading the same serial port interleave each other's replies. The
  lock file stops the miner from doing this to itself; do not start a second one.
* **`--bench` takes minutes** - that is expected. A difficulty-655 job searches
  up to 65,501 hashes, about 36 s per run.

## Limitations, honestly stated

* The core is AVR assembly. It has only been run on Mega 2560 boards; the
  generator emits instructions any AVR should execute, but only the AVR toolchain
  is exercised here.
* The reward figures are measurements on one account over one period. Kolka's
  `reward_div` changes as the network's total hashrate changes, so the DUCO/hour
  numbers will drift; the *relative* speedups are the stable part.
* The account allows 2 concurrent miners, so more boards do not help beyond that.
* The pool-side share race ("BAD Incorrect result", about 11% of shares) is not
  fixable from the miner side.
* `Settings.cfg` stores the mining key base64-encoded. That is not safe to share;
  it is gitignored for that reason.

## Is a custom miner allowed?

The code is MIT licensed and the official Duino-Coin README lists community
miners, so publishing a fork is fine. Their terms of service are less clear-cut
about running one: they "recommend using only the official or verified mining
programs", and state that "attempting to create your own mining software, or
modifying an official program may lead to account suspension or banning ... if a
modified program were to have an issue". Community software is explicitly allowed
as long as it complies with the rules.

What actually gets accounts flagged, and what this project does not do:

* **reporting a hashrate the hardware cannot produce.** The number submitted is
  the board's own nonce count divided by the elapsed microseconds it printed,
  exactly the calculation `AVR_Miner.py` does, and the miner checks
  `sha1(prevHash + nonce) == expectedHash` locally before submitting.
* **using a difficulty tier the hardware is not suited for** - the terms forbid
  emulating a differently powered device. The tier here is derived from the
  measured hashrate with the same thresholds the official AVR miner uses
  (> 1000 H/s `DUE`, > 550 `ARM`, > 380 `MEGA`, otherwise `AVR`), and since the
  2025 pool migration the node assigns difficulty dynamically from the hashrate
  it measures, so the tier string is only a hint.
* **spamming the pool or exceeding the miner allowance.** One socket per board,
  reused until the node closes it, reconnect instead of a new connection, no
  second instance (lock file per port set), and a mining key so nobody else can
  mine under the username.

I have asked the Duino-Coin Discord for a definitive reading of these rules and
will update this section when they reply.
