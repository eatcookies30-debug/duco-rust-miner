# Duino-Coin Rust Miner for Arduino AVR boards

A Duino-Coin AVR mining setup, in two parts:

* **`miner/`** - a replacement for `AVR_Miner.py` written in Rust with **no
  external crates** (std only), so there is nothing to install with pip.
* **`firmware/`** - the sketch flashed onto the board. Its SHA-1 nonce search is
  an AVR assembly core generated by `firmware/asm_core`, because GCC cannot keep
  SHA-1's five 32-bit state variables in registers on the AVR. Two sketches are
  provided: `firmware/asm_sketch` for a Mega 2560 and
  `firmware/nano_i2c_sketch` for an ATmega328P board (Nano, Uno, Pro Mini). Both
  take jobs over USB serial and over an I2C rig bus.
* **`firmware/tiny_core` / `firmware/tiny85`** - the same protocol for boards with
  only 8 KB of flash, where a sketch does not fit and arduino-cli has no board
  definition for the chip. It is plain C driven straight from the registers, so
  it needs `avr-gcc` and `avrdude` instead of arduino-cli.

Both parts talk the standard **DUCO-S1** protocol, so the pool, the difficulty
handling, the reward and the account are exactly the same as with the official
miner. Only the speed and the reliability change.

## Results

Everything below was measured on the two board families these sketches target -
a Mega 2560 and a Nano 328P clone - with the same benchmark (`miner --bench`,
which asks each board for nonces 50, 9,999, 42,424 and 65,500 and reports the
nonce and the elapsed time the board itself prints). The flash figures are what
arduino-cli 1.4.1 reports for the sketch as it is in this repo; the bare-metal
row is what `firmware/tiny85/build.sh atmega328p` measures with avr-gcc 7.3.0.

| firmware | board | flash | H/s per board | vs stock 4.3 on the same board |
|---|---|---|---|---|
| `firmware/official_sketch` (stock 4.3) | Mega 2560 | 13,670 B | 338 | 1.00x |
| `firmware/c_core` (optimised C) | Mega 2560 | 36,196 B | 1,239 | 3.66x |
| `firmware/asm_sketch` (assembly core) | Mega 2560 | 40,562 B | **1,824** | **5.40x** |
| `firmware/official_sketch` (stock 4.3) | Nano 328P | 13,072 B | 340 | 1.00x |
| `firmware/nano_i2c_sketch` (looped core) | Nano 328P | 26,100 B | **1,759** | **5.17x** |
| `firmware/tiny85` (bare metal, no Arduino core) | Nano 328P | 4,510 B | 763 | 2.24x |

The I2C glue is the same code in both sketches. On a Mega it adds 2,638 B
(37,924 B without it); on a Nano it adds 5,780 B (20,320 B without it), most of
which is the Wire library itself and the job ring the receive interrupt fills.
Driven over the I2C bus rather than USB serial, the same Nano sketch measures
1,590 H/s, which is 4.68x the stock sketch on that board. The bare-metal build
measures 763 H/s on the same Nano over USB serial and 727 H/s over the I2C bus;
it is the firmware that would fit an 8 KB chip, and it is about 43% of the
assembly core's speed (see [A core for an 8 KB board](#a-core-for-an-8-kb-board)).

Typical bench output for the assembly core on a Mega:

```
/dev/ttyACM0: DUCOID1234567890ABCDEF - test nonce 50 in 28240 us -> 1770.54 H/s
  diff 100: found nonce 9999 in 5.496152 s -> 1819.27 H/s OK
  diff 655: found nonce 42424 in 23.288248 s -> 1821.69 H/s OK
  diff 655: found nonce 65500 in 35.9504 s -> 1821.95 H/s OK
```

Two boards at 1,824 H/s produced about 1,890 accepted shares per hour, and the
account balance grew by 0.135 DUCO/hour measured against `server.duinocoin.com`
(442 accepted shares in 14 minutes). That is 47% more hashrate than the optimised
C firmware on the same boards and 5.4x the stock 4.3 sketch.

Kolka pays roughly `2 * ln(reported hashrate) / reward_div` per accepted share
with a `0.96^(miners - 1)` penalty, and difficulty is fixed at 128 for this
tier, so a miner also earns more shares per hour in proportion to its hashrate.
Hourly income therefore goes like `hashrate * ln(hashrate)`, not like hashrate
alone.

## Why the assembly core is faster

GCC ends up spilling SHA-1's state to RAM: 70 unrolled rounds need 24 live
registers, and the AVR has 32, of which the compiler uses for addressing and
the decimal-digit counter. The generated core instead keeps the state in six
register groups that **rotate** through the `a,b,c,d,e` roles one group per
round, so the role shift is a change of which group the next round names -
**no copies at all**:

```
G0 r16-19   G1 r20-23   G2 r2-5   G3 r6-9   G4 r10-13
G5 r14,r15,r30,r31      scratch: r24-27
```

What that buys over the C version:

* **no state copies** - the round's new `a` is accumulated directly in the group
  the previous round's `e` vacated (the C version spends 8 `movw` pairs a round
  on this);
* **phase constants in four instructions** - AVR has no `add reg, imm`, and only
  r16-r31 take immediates at all. Pinning the scratch group to r24-r27 lets
  `+0x5a827999` be done with `subi/sbci` of the two's complement (4 cycles)
  instead of four `lds` plus four `add` (12 cycles): 3.5% of the whole hash;
* **schedule words 16, 17 and 20 are written by C once per job** - they never
  depend on the nonce, so the core does not reload them into scratch every
  attempt (24 memory instructions per hash);
* **the digest compare is lazy** - only the most significant byte of the first
  word is loaded for the ~99.9% of attempts that fail there;
* **the last three schedule rounds skip their store** - a word is only read back
  three, eight, fourteen and sixteen rounds later, so rounds 77-79 never need to
  write it out.

The core is 7,453 instructions / 8,737 cycles at 16 MHz, i.e. 549 us per hash,
which is within 1% of the instruction-count floor. The schedule (16 `lds` + 12
`eor` + 5 shifts + 4 `sts` per round, 61 rounds) is 40% of the work and
`lds`/`sts` cost two cycles whatever the addressing mode, and AVR has no barrel
shifter, so `rotl5` is unavoidably a 20-instruction `rol` chain.

## Two cores, one generator

The unrolled core does not fit on a 328P. With the same hash code and the DUCOID
library but no I2C at all it is already 30,708 B, 99% of a Nano's 30,720 B of
program flash; add the Wire library and the I2C glue and the build stops with
`text section exceeds available space in board`. So the 328P sketch uses a core
written to be small, and the Mega keeps the unrolled one. Both come from the same
generator: `python3 gen_asm.py --compact` emits the looped version,
`python3 gen_asm.py` the unrolled one.

The role shift repeats every six rounds, so the compact core cuts each 20-round
phase into a six-round body that runs three times, with the leftover rounds
emitted inline: 3,625 instructions of code instead of 7,453, which is the 8 KB
that a Nano does not have. Inside the loop body the schedule pointer `Z` stands
in for the absolute `MSG[...]` addresses - a round stores at `Z+60` and steps
back to the next round's base - and since `Z` advances exactly four bytes a
round, comparing its low byte against the end of the window is the loop test, so
there is no counter register at all. The instruction and cycle counts the
generator prints are the emitted code, not the code executed: the compact body is
jumped through three times per phase, so a Nano hash still runs about 70 rounds.

Giving up that code size costs a little speed: on the same Nano the unrolled core
measures 1,815 H/s and the looped core 1,759 H/s, about 3% apart. The compact
group set is also one register pair different - it uses r28:r29 for part of the
state instead of r30:r31, because r30:r31 are needed for the pointer - and since
r28:r29 is the pair GCC uses as the stack frame pointer, the compact core pushes
and pops them on entry and before every return, which is what makes it safe to
call from a function with local variables.

## A core for an 8 KB board

An ATmega8 or an ATtiny85 has 8 KB of program flash and 512-1,024 B of RAM, and
the standard Arduino AVR core has no board definition for either of them:
`boards.txt` covers the 168/328 and the 1280/2560 chips only. So there is no
sketch to build for a chip that small, and even a skeleton sketch that searches
with the small core, takes a job over Serial and answers on the Wire bus
measures 5,514 B on a 328P with arduino-cli 1.4.1 before the board id, the
timing and the reply line are added. `firmware/tiny_core` and
`firmware/tiny85` are the firmware for those boards: the same protocol and the
same reply line, driven from registers with no Arduino libraries, in 4,510 B -
smaller than the skeleton sketch that only does part of the job.

**The core** (`tiny_core/tiny_hash.c`) is a single looped round body:

* the schedule is a **16-word rolling window** rather than 80 words. `W[i]` is
  read back at rounds `i+3`, `i+8`, `i+14` and `i+16`, and the round that
  overwrites slot `i & 15` is round `i+16` - the last round that word is needed
  in - so 64 bytes of RAM is enough instead of 320;
* rounds 0-9 depend only on the previous hash, not on the nonce, so they are
  computed **once per job** and the search starts from that state;
* the nonce is walked as **decimal digits** instead of being formatted every
  attempt, so the search loop never divides;
* the state is plain local variables, so GCC decides where it lives. On a 328P
  it stays in registers; on an ATtiny85, which has eight registers in total, it
  spills to RAM and the hash still runs.

`check_tiny_core.py` generates test vectors with `hashlib`, runs them through the
core, and also reports what the core costs on each chip:

```bash
cd firmware/tiny_core && python3 check_tiny_core.py
```

```
tiny core: 408 cases checked, 0 failures
cost of the core on AVR chips (-Os):
  atmega328p   1946 B of code,  168 B of RAM  (of 32768 B flash, 2048 B RAM on chip)
  atmega168p   1946 B of code,  168 B of RAM  (of 16384 B flash, 1024 B RAM on chip)
  atmega8      1940 B of code,  168 B of RAM  (of 8192 B flash, 1024 B RAM on chip)
  atmega16     1946 B of code,  168 B of RAM  (of 16384 B flash, 1024 B RAM on chip)
  attiny85     1964 B of code,  168 B of RAM  (of 8192 B flash, 512 B RAM on chip)
```

**The whole miner** (`tiny85/duco_tiny.c`) is the core plus everything a sketch
would get from the Arduino core, done from registers: a TWI slave interrupt
handler, a UART driver, the DUCOID read out of the boot signature row, and Timer
1 to time a search.

```bash
cd firmware/tiny85
./build.sh                       # atmega328p, the Nano/Uno chip
./build.sh atmega8
./build.sh atmega328p "-DDUCO_DEBUG"     # prints every job the board parses
```

| chip | flash | RAM | |
|---|---|---|---|
| ATmega328P (Nano, Uno) | 4,510 B | 713 B | measured on a Nano 328P clone |
| ATmega168P | 4,510 B | 713 B | same driver as the 328P |
| ATmega8 | 4,258 B | 729 B | 51% of an 8 KB chip, 71% of its 1 KB of RAM |
| ATmega16 | 4,392 B | 729 B | |
| ATtiny85 | 2,236 B | 237 B | compiles; the bus driver is compiled out, see below |

There is no sketch for arduino-cli to build, so it goes on with avrdude:

```bash
avrdude -c arduino -p atmega328p -P /dev/ttyUSB0 -U flash:w:duco_tiny_atmega328p.hex
```

The board then speaks the same protocol as the sketches - `prevHash,targetHash,difficulty\n`
in, `nonce,elapsed,DUCOID\n` out, with the nonce and the elapsed time as binary
digits on the serial port and decimal over I2C - so the Rust miner drives it
without any change. `--bench` against a bare-metal Nano 328P clone:

```
/dev/ttyUSB0: DUCOID0123456789ABCDEF01 - test nonce 50 in 65489 us -> 763.49 H/s
  diff 100: found nonce 9999 in 13.009329 s -> 768.60 H/s OK
  diff 655: found nonce 42424 in 55.619646 s -> 762.75 H/s OK
  diff 655: found nonce 65500 in 85.944262 s -> 762.12 H/s OK
```

and `firmware/i2c_bench` on a Mega drove that same bare-metal board over the bus
for 240 s: 7 jobs sent, 7 replies with the nonce the bench expects, no job byte
unacknowledged, 727 H/s. That is 43% of the assembly core on the same board: the
looped C round body costs about 2.3x the cycles of the unrolled assembly one,
which is the price of fitting in a fifth of the flash.

**ATtiny85.** The core and the job handling fit with room to spare - 2,236 B of
the 8,192 B of flash and 237 B of the 512 B of RAM - but the ATtiny85 has no TWI
module at all: `iotnx5.h` defines no `TW*` registers, so serving the bus there
means driving it through USI in two-wire mode, which is a different driver and
another 1-2 KB. `build.sh attiny85` compiles with the bus driver and the UART
compiled out. That is a fit and instruction-set check, not a board you can hand
jobs to, and nothing here was run on ATtiny85 hardware.

## Requirements

* A board. `firmware/asm_sketch` is for a **Mega 2560** (40,144 B, 15% of its
  253,952 B of program flash) or any AVR with 64 KB or more.
  `firmware/nano_i2c_sketch` is for an **ATmega328P** board - Nano, Uno,
  Pro Mini - where the looped core takes 25,714 B (83% of a Nano's 30,720 B,
  80% of an Uno's 32,256 B) and 1,488 B of the 2,048 B of RAM.
  The unrolled core does not fit in a 328P: on its own it is 30,708 B, and with
  the Wire library in the sketch the build fails with
  `text section exceeds available space in board`.
* A board with 8 KB of flash - **ATmega8** or **ATmega16** - takes
  `firmware/tiny85`, which has no Arduino core in it and so needs `avr-gcc` and
  `avrdude` rather than arduino-cli. The toolchain arduino-cli installs works,
  and `build.sh` finds it.
* [`arduino-cli`](https://arduino.github.io/arduino-cli/installation/) to flash
  (the Arduino IDE works as well - open `firmware/asm_sketch/asm_sketch.ino`).
* Rust 1.70+ to build the miner. No crates, no network access needed to build.
* Python 3 only for the generator and the verification scripts, and for the two
  helper scripts. No third-party packages.
* Linux is the platform everything here was tested on. The miner itself is plain
  std Rust, so it should work wherever a serial device can be opened by path
  (on macOS that is `/dev/tty.usbmodem*`, on Windows the `COM` ports are not
  openable that way - use the official Python miner on Windows).

## Quick start

```bash
git clone https://github.com/eatcookies30-debug/duco-rust-miner
cd duco-rust-miner

# 1. flash the assembly core (detects the boards automatically)
./scripts/flash.sh firmware/asm_sketch
#    or explicitly:
./scripts/flash.sh firmware/asm_sketch /dev/ttyACM0 /dev/ttyACM1

#    a Nano, Uno or Pro Mini takes the looped core; boards whose name
#    arduino-cli cannot read need --board
./scripts/flash.sh --board arduino:avr:nano firmware/nano_i2c_sketch /dev/ttyUSB0

#    a board with only 8 KB of flash has no room for the Arduino core at all:
#    firmware/tiny85 is the same protocol built from registers
cd firmware/tiny85 && ./build.sh atmega8 && cd ../..
avrdude -c arduino -p atmega8 -P /dev/ttyUSB0 -U flash:w:firmware/tiny85/duco_tiny_atmega8.hex

# 2. build the miner
cd miner && cargo build --release

# 3. see what the boards can actually do, offline, without an account
./target/release/duco-miner --bench --ports /dev/ttyACM0,/dev/ttyACM1

# 4. mine
./target/release/duco-miner --user your_username \
    --ports /dev/ttyACM0,/dev/ttyACM1 --key your_mining_key
```

You can point the miner at the official miner's config file instead of passing
flags:

```bash
./target/release/duco-miner --config "Duino-Coin AVR Miner 4.3/Settings.cfg"
```

`Settings.cfg.example` is a template; copy it to `Settings.cfg` and edit it.

## Command line

| flag | meaning |
|---|---|
| `--config FILE` | read username, ports, key and timeouts from the official `Settings.cfg` |
| `--user NAME` | Duino-Coin username |
| `--key KEY` / `--mining-key KEY` | mining key (base64 or plain; see below) |
| `--ports /dev/ttyACM0,/dev/ttyACM1` | serial ports of the boards (up to 2) |
| `--pool ip:port` | skip the pool picker and use a specific node |
| `--tier AVR\|MEGA\|ARM\|DUE` | force the difficulty class instead of deriving it from the measured hashrate |
| `--report-time SECS` | how often to print the running totals (default 60) |
| `--board-timeout SECS` | deadline for one board to answer one job (default 120) |
| `--rounds N` | stop after N shares (useful for testing) |
| `--bench` | hashrate benchmark straight against the boards, no network, no account |
| `--mock` | run a fake pool node on 127.0.0.1:7913 and mine against it - tests the whole protocol without an account |
| `--ping` | print the pool node the picker gives you and its greeting round trip |
| `--version` / `-V` | print the miner version (put it in bug reports) |
| `DUCO_DEBUG=1` | dump the raw bytes the boards send, with timestamps, to stderr |

`DUCO_MINING_KEY=<key>` is read from the environment too. `Settings.cfg` keys
that are honoured: `username`, `avrport`, `mining_key`, `identifier` (the rig
identifier sent with each share, one per board), `periodic_report`,
`avr_timeout` (how long a board has to answer one job) and `soc_timeout` (how
long the pool socket has to answer one request).

## The mining key

Duino-Coin accounts can have a **mining key**: a secret sent with every job
request so nobody who only knows your username can mine into your balance. The
official `AVR_Miner.py` stores it **base64-encoded** in `Settings.cfg`:

```
mining_key = aGVsbG8=      # the key is "hello"
```

The miner here understands both the encoded and the plain form, and it checks
the key against the account service **before** mining so a wrong key is not
quietly ignored:

```
account your_username: mining key accepted
```

Use `scripts/set-mining-key.sh` to store a verified key:

```bash
./scripts/set-mining-key.sh                     # asks, verifies, saves
./scripts/set-mining-key.sh "your key"          # non-interactive
./scripts/set-mining-key.sh --clear             # remove it
```

It points at `./Settings.cfg` by default, or at the file named by
`DUCO_SETTINGS`. Base64 is obfuscation, not encryption: keep the file out of the
repo (it is gitignored) and do not paste it into an issue.

`scripts/balance.sh` prints the balance, the trust score, the number of miners
the account allows, the registered miners, and whether the key in Settings.cfg is
the one the account expects.

## Mining over an I2C rig

Both sketches also speak the I2C (TWI) protocol used by community Duino-Coin
rigs, so a board can be driven by an ESP32, an ESP8266, a Raspberry Pi or
another Arduino instead of being plugged into a PC. The Rust miner itself talks
USB serial only; the I2C path is for a rig master. The board side is
`i2c_slave.h` / `i2c_slave.cpp`, the same two files in both sketches.

Wire the bus like any other I2C pair, using the TWI pins of each board:

```
ATmega328P (Nano, Uno, Pro Mini):  SDA = A4,  SCL = A5
ATmega1280/2560 (Mega):            SDA = D20, SCL = D21
```

SDA to SDA, SCL to SCL, ground to ground. The Mega is the trap here: its I2C
lines are digital pins 20 and 21, not its analog A4/A5, so wiring a Mega to
A4/A5 connects it to nothing. The glue knows which pins belong to the bus and
puts pull-ups on them; a 328P board needs those internal pull-ups because it has
no external resistors on the lines, and a Mega 2560 has them onboard already.

At startup the board walks addresses 1 to 126 and takes the first one nobody
acknowledges, then prints what it chose on the serial port
(`I2C slave address: 1`). Those numbers move whenever a board resets, so on a rig
where the address is how a share gets attributed, give each board its own:
build it with `-DSLAVE_ADDRESS=<1-126>`, which `scripts/flash.sh` passes through
as `--define SLAVE_ADDRESS=3`. A fixed address that is already held is retried a
few times, and if it never comes free the board falls back to the scan and takes
the first free address, so it keeps mining instead of sitting out; the number it
prints at startup is always the one to talk to. Before probing, the board checks
that SDA and SCL are both high: probing in the middle of somebody else's
transaction leaves the TWI module waiting for a start condition with SDA held
low, which jams the bus for every board on it.

**Every board has to be a different name at the pool.** A board's identity is the
sixteen hex digits of the eight byte device id in its boot signature row. Clone
boards often ship with that row blank, in which case every board of that kind
reads 0xFF and reports the same id, and the pool counts them as a single miner.
The address the board claims is written into the last two digits of its id, which
keeps the id the length the protocol expects and makes each board its own:

```
signature row 3A 7F 2C 91 4D 6E 0B 58, address 1  ->  DUCOID3A7F2C914D6E0B01
signature row 3A 7F 2C 91 4D 6E 0B 58, address 2  ->  DUCOID3A7F2C914D6E0B02
signature row all 0xFF,              address 3  ->  DUCOIDFFDFFFDFFFFFFF03
```

A board that never joins a bus has no address to fold in, so it keeps the plain id
its signature row gives it.

The exchange is the one from
[ricaun/DuinoCoinI2C](https://github.com/ricaun/DuinoCoinI2C):

* the master pushes `prevHash,targetHash,difficulty\n`, one byte per
  transmission;
* the board searches and then answers `nonce,elapsedMicros,DUCOID\n`, served one
  byte at a time in response to `requestFrom(address, 1)`;
* while the search is still running, every poll is answered with a bare `\n`,
  which is how the reference masters read "nothing yet" and simply poll again.
  The search runs in the main loop while the TWI interrupts serve the bus, so a
  board answering a rig is still mining.

Note that the reply is **decimal** over I2C and **binary** on the serial port.
That is what the reference rig implementations do, and it is why the Rust miner
(serial) and an ESP rig master (I2C) read the same field differently.

### Keeping the job buffer safe

Two things the glue has to get right, because both are easy to get wrong in a way
that makes a board look dead rather than slow:

* **the master keeps pushing while the board is still searching.** The job buffer
  is a 256 byte ring, a little more than two jobs wide. `jobHead` is written only by
  the receive interrupt and `jobTail` only by the main loop, so consuming one job
  cannot lose the bytes of the next one. When the ring is full the interrupt
  ignores further bytes and sets a flag, and the main loop clears the whole buffer
  before it reads it again: a half stored job is dropped rather than spliced onto
  the bytes that follow it, which would otherwise be parsed as a job with the
  wrong hashes.
* **the interrupt fills the buffer while the main loop is scanning it.** The scan
  for a job's newline has to compare against the length it snapshotted when it
  started. The first version compared against the live length instead, so a job
  still in transit looked finished at the point the scan had reached, one character
  of it was silently dropped, the hashes came out short, the job was refused, and
  the board never answered. `firmware/i2c_slave_test` reproduces that on a desktop
  with a second thread pushing job bytes while the scan runs: against the snapshot
  the glue accepts all 20 jobs the thread pushes, against the live length it
  accepts none of them.

### More than one board on the bus

Every slave hangs off the same two wires, so a rig of N boards on one master is
three nets, not N pairs:

```
                master  (Mega, Uno, ESP32, ...)
                SDA ─┬─ A4 ─ A4 ─ A4 ─ A4 ─ ...
                SCL ─┼─ A5 ─ A5 ─ A5 ─ A5 ─ ...
                GND ─┴─ GND ─ GND ─ GND ─ GND ─ ...
```

Every board's internal pull-up ends up in parallel, so each board you add makes
the lines stronger: ten 328P boards give roughly 4 kOhm on each line, which the
bus is happy with. Bus capacitance grows with every board and every foot of wire,
so keep the leads short, and if replies start getting dropped, cut
`BUS_CLOCK_HZ` in the bench to 50000 before blaming a board.

Give each board its own address as you flash it, one board at a time:

```bash
port=/dev/ttyUSB0      # whatever port arduino-cli reports the board on
for n in 1 2 3 4 5 6; do
  ./scripts/flash.sh --board arduino:avr:nano --define SLAVE_ADDRESS=$n \
                     firmware/nano_i2c_sketch "$port"
done
```

`firmware/i2c_bench` is the master for that arrangement. It walks addresses 1 to
126, adds every slave that answers, and then drives all of them at once: each
slave gets its own job, and the master polls each slave one byte at a time in
turn before moving to the next one, so N boards search at the same time instead
of one at a time. A board that is still searching answers a poll with a bare
newline and the master moves on, which is what stops one slow board from holding
the bus while the others sit idle. The bus is rescanned every 30 s, so a board
plugged in later joins without restarting the master. `MAX_SLAVES` is 10; raise
it for a bigger rig, keeping in mind that the master carries a 48 byte reply
buffer per slave, so a 328P board acting as master runs out of RAM long before a
Mega does. With one board on the bus, a run looks like this:

```
Slave at address 1
slave 1: nonce 9999 OK, 1590 H/s  (1/1 so far)
Totals: 1 slaves, 1 jobs, 1 correct, 0 wrong, 0 of 86 job bytes unacked, 1590 H/s across the 1 mining slaves
```

The job the bench sends is SHA-1(`ba29a15896fd2d792d5c4b60668bf2b9feebc51d` +
`9999`), so a correct slave answers with 9999; the third field of the reply is the
board's own DUCOID. Driving a Nano this way measures 1,590 H/s against 1,759 H/s
on the same board over USB serial: the search runs in the main loop while the TWI
interrupts serve the bus, so the difference is the cost of the polls, since the
master has to ask for the answer one byte at a time. Those figures are from a
single slave on the bus - the round-robin over several boards at once has not been
measured, so per-board hashrate with N boards searching simultaneously is still
untested.

The job and reply handling can also be exercised on a desktop, without a board,
with `firmware/i2c_slave_test`:

```bash
cd firmware/i2c_slave_test
for flags in "" "-DSLAVE_ADDRESS=5" "-DSLAVE_ADDRESS=5 -DTEST_ADDRESS_TAKEN"; do
  g++ -Wall -pthread -I stub -x c++ $flags \
      slave_test.cpp ../asm_sketch/i2c_slave.cpp -o slave_test
  ./slave_test | tail -2
done
```

It drives `i2c_slave.cpp` through the same sequence a master uses and checks the
parsed job, the reply line, the newline-while-searching behaviour, the buffer
limits, malformed jobs, and - with a second thread playing the receive interrupt -
that a job is never taken before its newline has arrived. The three builds cover
an auto-claimed address, a fixed one, and a fixed one that is already held by
another board. Currently 33 checks per build, 0 failures in all three.

## How the PC-side miner differs from `AVR_Miner.py`


| | official `AVR_Miner.py` | this miner |
|---|---|---|
| dependency | Python + pip + `serial` + `requests` | one static binary, std only |
| serial port | reopened for every job, which resets the board | opened once per session; the board keeps running |
| serial read | no timeout | hard deadline per job, so a stuck board cannot stall the run |
| reply framing | takes whatever arrives | discards a reply left over from an abandoned job, then verifies `sha1(prevHash + nonce) == expectedHash` locally before submitting |
| board recovery | gives up after a few failures | reopens the port, which toggles DTR and resets the sketch |
| pool connection | reconnects on error | reconnects on EOF or timeout, and after three consecutive failures asks the pool picker for a different node |
| pool replies | one `recv(limit)` | line-based with the unread tail kept, so split or bunched replies are not lost |
| mining key | decoded, never validated | decoded **and** validated against the account service before mining |
| concurrency | nothing stops two instances | a lock file per port set (`/tmp/duco-miner-<ports>.lock`) |
| offline testing | none | `--bench` (boards only) and `--mock` (protocol only, no account) |

## Verifying the assembly core

The cores are machine-generated, so they come with the checks that generated
them:

```bash
cd firmware/asm_core
python3 gen_asm.py                                    # instruction and cycle counts
python3 gen_asm.py --compact                          # the looped core, same output style
python3 sim_check.py                                  # simulated AVR vs hashlib
python3 sim_check.py --compact                        # the looped core
```

which currently prints:

```
full core: 7453 instructions, 8737 cycles
  checked 205 nonces, failures: 0
  random hash/nonce failures: 0
  false positives: 0
compact core: 3625 instructions, 4209 cycles
  checked 205 nonces, failures: 0
  random hash/nonce failures: 0
  false positives: 0
```

Those counts are the emitted code, not the rounds executed - the compact core's
loop body is jumped through three times per phase. What the simulator checks is
that the digest the core produces equals `hashlib`'s, for both cores.

Three further levels of verification, in order of how much hardware they need:

1. **`sim_check.py`** - a small AVR simulator (only the opcodes the cores use)
   runs the generated core for 205 nonces plus 400 random hash/nonce pairs and
   compares the digest with Python's `hashlib`: 0 failures. This is what catches
   register-aliasing and flag bugs before they reach a board.
2. **`build_trace.py` + `trace_test/`** - builds a sketch that stores the state
   after every round and compares it with a C reference: `bad rounds: 0`.
3. **`hit_test/`** - a standalone sketch with hardcoded targets: finds nonce 50
   for the known digest and correctly reports "no match" for a wrong target.

`firmware/asm_core/board_probe.py` is a plain serial probe (no pool, no account)
for timing searches on a board; it needs `pyserial`:

```bash
pip install pyserial
python3 firmware/asm_core/board_probe.py /dev/ttyACM0
python3 firmware/asm_core/board_probe.py /dev/ttyUSB0 --random 10
```

The probe sends jobs whose nonce is known in advance and checks the nonce each
board reports. Every board used for the figures above was put through it: 10 jobs
per board, every nonce found.

In addition, the miner re-computes `sha1(prevHash + nonce)` itself before
submitting any share, so a board that ever returned a wrong nonce would be
rejected by the miner rather than paid for.

The unit tests in the Rust miner cover the SHA-1 implementation, the binary
reply parsing, and the base64 mining-key normalisation:

```bash
cd miner && cargo test
```

## AVR gotchas worth knowing

Each of these is a plausible way to end up with a board that hashes silently
wrong. The first list is what the generator has to get right:

* `lds`/`sts` move **one byte**, not a 32-bit word - a 32-bit value needs four of
  each. The classic "LDS loads two bytes" mistake leaves every odd register
  holding garbage;
* `ldi`, `subi`, `sbci` only work on r16-r31, which is why the scratch group is
  pinned to r24-r27;
* `r1` is the zero register by ABI - the rotate-by-1 uses `adc reg, r1`;
* `r0` is ordinary writable space. It is easy to assume the first register is
  reserved, so a probe on a Nano (`mov r0, r4`, then shifting r4 left through r0)
  was run before the rotate-by-5 and rotate-by-30 helpers were written to use it
  as scratch;
* `ldd`/`std` displacements are a 6-bit field, so a pointer reaches 63 bytes at
  most. That is why the compact core's schedule window is 60 bytes wide and
  steps with `adiw r30, 60` then `sbiw r30, 56`; the immediate in `adiw`/`sbiw`
  also tops out at 63, and there is no `subiw` at all;
* conditional branches reach only 63 words, so the compare's failure handlers are
  inlined per word instead of chained to one distant label;
* the hit flag must come back as an inline-asm output register, not a global:
  without a memory clobber GCC hoists the global's load out of the nonce loop and
  every attempt looks like a miss;
* globals referenced only from asm must be non-`static` and marked
  `__attribute__((used))`, because arduino-cli builds with `-flto` and otherwise
  deletes them;
* `.inc` files are not reliably copied by arduino-cli, so the generated core is
  included as a `.h`.

Four more that only bite a build with no Arduino libraries in it, like
`firmware/tiny85`:

* **AVR's `int` is 16 bits wide**, so a literal shifted past that width loses
  bits. `tail[...] |= 0x80u << 24` is a shift past the width of the type the
  literal is written in, and the SHA-1 padding byte quietly disappears from the
  message. On a board it looks like a core that finds two- and three-digit
  nonces and misses one- and four-digit ones - which is what the probe showed
  before the literal was cast to `uint32_t` first. `check_tiny_core.py` cannot
  catch this, because on a desktop the same expression is well defined.
* **TWCR is not a set/clear register.** Every write replaces the whole byte, so
  an acknowledge that leaves `TWIE` out switches the bus interrupt off for good.
  The board then answers the first poll and never answers again, and the master
  hangs waiting for a transmission that will never finish.
* **A START that never completes has to be abandoned by turning the module off**
  (`TWCR = 0`). With `TWEN` still set and `TWSTA` pending, the TWI keeps asking
  for a start condition and holds SDA low, which jams the bus for everything
  attached to it, the board that did it included.
* **The baud divisor has to be rounded.** `(F_CPU/16 + BAUD/2)/BAUD - 1` is
  UBRR 8, i.e. 111,111 baud, 3.5% off the 115,200 a PC asks for; truncating
  `(F_CPU/16)/BAUD - 1` gives UBRR 7, 125,000 baud, 8.5% error, and the replies
  arrive as garbage. 3.5% is well inside what both ends tolerate, which is why
  the miner at 115200 reads the bare-metal board fine.

## Troubleshooting

* **"Sketch uses 37324 bytes (115%) of program storage space"** or **"text
   section exceeds available space in board"** - the unrolled core does not fit
   in an ATmega328P's 30,720 B of program flash once the Wire library is in the
   sketch. Flash `firmware/nano_i2c_sketch` on a Nano, Uno or Pro Mini;
   `firmware/asm_sketch` is for boards with at least 64 KB of program flash.
* **"Permission denied" opening `/dev/ttyACM0`** - serial ports belong to the
  `dialout` group on most Linux distros:

  ```bash
  sudo usermod -aG dialout "$USER"   # then log out and back in
  ```

* **"no reply from /dev/ttyACMx within Ns"** - the board was given a job and did
  not answer. The miner responds by reopening the port, which resets the sketch.
  If it happens to every board at once, the pool node is usually the cause, not
  the hardware: the node closes a connection whose share has not arrived, and a
  board left searching a dead job looks dead for the whole allowance.
* **Nothing answers on the I2C bus** - the two boards need a common ground, and
  the two ends have to be on each board's TWI pins, which are not the same pins
  on every board: A4/A5 on a 328P, D20/D21 on a Mega. `firmware/i2c_bench` prints
  the pins it is using when it finds no slave. The slave takes the first address
  nobody acknowledges, so the number the sketch prints at startup is the address
  to talk to, and `firmware/i2c_bench` walks the whole range, addresses 1 to 126.
  A slave that is still searching answers every poll with a newline, so a master
  that reads a line gets an empty one and polls again - that is the reference
  behaviour, not a hang.
* **A bare-metal board from `firmware/tiny85` prints nothing at boot** - it runs
  its UART at 111,111 baud (UBRR 8), which is what a 115,200 terminal reads
  correctly; a truncated divisor (UBRR 7, 125,000 baud) is 8.5% off and the
  replies come back as garbage. Before it prints anything the board walks
  addresses 1 to 126 looking for a free one, so if something else on the bus is
  holding SDA low at that moment it says `I2C: no free bus address`, mines over
  serial only, and retries the bus every five seconds. Flashing it with avrdude
  writes only the application pages, so the bootloader is left alone and an
  Arduino sketch can be uploaded afterwards with arduino-cli.
* **"BAD Too high starting difficulty"** - normal, once per connection per board.
  The node starts the tier probe at difficulty 512 and then drops to 128; the
  first nonce found against the old target is not valid for the new one. The
  official miner loses the same shares.
* **"BAD Incorrect result"** - a pool-side race: the node sends `prevHash` +
  `expectedHash`, the board spends seconds finding the nonce, and by the time the
  share is submitted the node has advanced the chain from other miners on that
  node, so the hash it recomputes uses a newer `prevHash`. Nothing in the
  firmware or the miner can avoid it, and it is why only accepted shares count.
* **Boards "time out" only when you run `--bench` while the miner is mining** -
  two processes reading the same serial port interleave each other's replies. The
  lock file stops the miner from doing this to itself; do not start a second one.
* **`--bench` takes minutes** - that is expected. A difficulty-655 job searches
  up to 65,501 hashes, about 36 s per run.

## Limitations

* The cores are AVR assembly. They have been run on Mega 2560 and Nano 328P
  boards; the generator emits instructions any AVR should execute, but only those
  two boards are exercised here.
* The I2C slave is the community rig protocol from `ricaun/DuinoCoinI2C`, and it
  was measured on a physical bus, not just in code: `firmware/i2c_bench` on a Mega
  2560 drove a Nano 328P slave over D20/D21 to A4/A5 at 100 kHz for 320 s, 12 jobs
  went out and 12 came back with the nonce the bench expects, with no job byte
  unacknowledged and no job needing a resend (1,590 H/s on that Nano). The same
  glue was checked with the roles swapped - bench on the Nano, Mega as the slave -
  and 9 jobs out gave 9 correct replies at 1,637 H/s. What has not been tested is a
  master from the reference rig implementations - ESP32, ESP8266, Raspberry Pi -
  since the bench in this repo is its own master and the master half of a real rig
  is somebody else's firmware.
* The bare-metal build in `firmware/tiny85` was measured on an ATmega328P Nano
  and nothing else. The ATmega8, ATmega16 and ATmega168P builds compile against
  the same register-level TWI and UART driver, but no board of those kinds was
  run here. The ATtiny85 build compiles - 2,236 B of flash, 237 B of RAM - with
  the bus driver compiled out, because that chip has no TWI module and would
  need a USI two-wire driver that is not written. So the 8 KB claim is that the
  whole miner fits in half of an ATmega8's flash with the bus path intact; the
  ATtiny85 line is a size and instruction-set check, not a working miner.
* The bare-metal job ring is 128 bytes, a little over one job wide, and while a
  search is running the board ignores the bytes that arrive on either path. That
  is deliberate: two masters writing into one ring is the only way a job line can
  end up spliced onto somebody else's bytes, and a spliced line still parses as a
  job - 40 hex characters, 40 hex characters, a difficulty - with the wrong
  target. Before that guard was in place, running `firmware/i2c_bench` and the
  Rust miner against the same bare-metal board at the same time had the board
  spend 13 seconds hunting a nonce that was never in the range and report 0 for
  jobs the serial probe had answered correctly seconds earlier. The rule is still
  one master per board: a board already mining does not take a second job until
  it has answered the first.
* The reward figures are measurements on one account over one period. Kolka's
  `reward_div` changes as the network's total hashrate changes, so the DUCO/hour
  numbers will drift; the *relative* speedups are the stable part.
* The account allows 2 concurrent miners, so more boards do not help beyond that.
* The pool-side share race ("BAD Incorrect result", about 11% of shares) is not
  fixable from the miner side.
* `Settings.cfg` stores the mining key base64-encoded. That is not safe to share;
  it is gitignored for that reason.

## Is a custom miner allowed?

The code is MIT licensed and the official Duino-Coin README lists community
miners, so publishing a fork is fine. Their terms of service are less clear-cut
about running one: they "recommend using only the official or verified mining
programs", and state that "attempting to create your own mining software, or
modifying an official program may lead to account suspension or banning ... if a
modified program were to have an issue". Community software is explicitly allowed
as long as it complies with the rules.

What actually gets accounts flagged, and what this project does not do:

* **reporting a hashrate the hardware cannot produce.** The number submitted is
  the board's own nonce count divided by the elapsed microseconds it printed,
  exactly the calculation `AVR_Miner.py` does, and the miner checks
  `sha1(prevHash + nonce) == expectedHash` locally before submitting.
* **using a difficulty tier the hardware is not suited for** - the terms forbid
  emulating a differently powered device. The tier here is derived from the
  measured hashrate with the same thresholds the official AVR miner uses
  (> 1000 H/s `DUE`, > 550 `ARM`, > 380 `MEGA`, otherwise `AVR`), and since the
  2025 pool migration the node assigns difficulty dynamically from the hashrate
  it measures, so the tier string is only a hint.
* **spamming the pool or exceeding the miner allowance.** One socket per board,
  reused until the node closes it, reconnect instead of a new connection, no
  second instance (lock file per port set), and a mining key so nobody else can
  mine under the username.

A question about this has been raised in the Duino-Coin Discord; this section
will be updated when a definitive answer arrives.
